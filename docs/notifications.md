# Dispatch notifications

When a dispatch is **created**, and again when it's **delivered**, the system
records a notification for each party it should tell:

- **created** → the customer ("your order is on its way") and the assigned
  driver ("new trip assigned")
- **delivered** → the customer ("your order has been delivered")

## AI-personalized copy

Each customer email's body is generated by Claude when `ANTHROPIC_API_KEY` is
configured — see [`crate::logistics::ai::notification_copy`] — falling back
to the exact fixed template shown above on any error (no API key, a network
problem, a rate limit). A misconfigured or rate-limited environment must
never block recording or sending a notification, so generation is attempted
inline and any failure is silently absorbed into the fallback; nothing about
this is best-effort in the sense of "might not happen" from the caller's
point of view — every notification always gets *a* body, AI-personalized or
not. Generation is skipped entirely (no Claude call at all) for an SMS, whose
wording must match its [DLT template](#sending-sms-through-msg91), and for a row
with no contact to send to, since nobody will ever see that copy.

## What "recording" means

Every notification lands in the `Notifications` table with a status:

| status | meaning |
| --- | --- |
| `QUEUED` | ready to send, but no provider is configured for its channel yet |
| `SKIPPED` | no contact on file for this party, nothing to send |
| `SENT` | delivery succeeded |
| `FAILED` | delivery was attempted and the provider reported an error |

Recording and delivery happen in the same request: right after a `QUEUED`
row is inserted, `Notification::deliver_queued_best_effort` calls
[`crate::logistics::notification::delivery`] to actually send it — MSG91 for
SMS, and for email either SMTP (Gmail by default) or
[Resend](https://resend.com). All are optional and read their credentials from
the environment:

| Channel | Variables |
| --- | --- |
| SMS (MSG91) | `MSG91_AUTH_KEY`, one `MSG91_TEMPLATE_*` per message, optional `MSG91_SENDER_ID` |
| Email (SMTP) | `SMTP_USERNAME`, `SMTP_PASSWORD`, optional `SMTP_FROM`, `SMTP_HOST`, `SMTP_PORT` |
| Email (Resend) | `RESEND_API_KEY`, `RESEND_FROM_EMAIL`; only used when SMTP isn't set |

A channel with no credentials configured behaves exactly as before this
feature existed: the row is left `QUEUED` rather than marked `FAILED` —
nothing was actually attempted, and it's ready to send the moment the
provider is configured. Delivery is best-effort either way: a failure only
updates that notification's own status, it never fails the dispatch
create/deliver request it's attached to.

## Sending email from a Gmail account

Resend only sends from a domain you have verified, so a `@gmail.com` sender has
to go through Gmail's SMTP server:

1. Turn on 2-Step Verification for the account, at
   <https://myaccount.google.com/security>.
2. Create an App Password at <https://myaccount.google.com/apppasswords>.
   Google shows 16 characters in groups of four; drop the spaces.
3. Set the variables wherever the API gets its environment:

   ```
   SMTP_USERNAME=akashshinde.logistics@gmail.com
   SMTP_PASSWORD=abcdefghijklmnop
   SMTP_FROM=Logistics Dispatch <akashshinde.logistics@gmail.com>
   ```

4. Check them by sending yourself a message, with no dispatch involved:

   ```
   cargo run --bin send_test_email -- you@example.com
   ```

5. Restart the API.

Things to know:

- A personal Gmail account can send about 500 messages a day, and Google may
  pause an account that looks like bulk mail. A verified domain on Resend or
  similar is the upgrade path when volume grows; it needs only a config change.
- Copies of everything sent appear in the account's **Sent** folder, and bounces
  and customer replies land in its inbox. Nothing in this system reads them.
- Changing the account's password revokes its App Passwords, and sends then fail
  until a new one is set.
- `QUEUED` rows recorded before a provider was configured are not sent
  afterwards, so turning email on doesn't send customers stale messages.

## Sending SMS through MSG91

Indian operators only deliver text matching a template approved on a DLT
portal, so an SMS is a template ID plus variable values rather than free text.
Numbers must be Indian mobiles: `+91 98765 43210`, `9876543210` and similar are
normalized, and anything else is marked `FAILED` without calling MSG91.

Set up, once:

1. Register the business, the sender ID and the four templates below on a DLT
   portal, under the service implicit category. This costs a one-time ₹5,900
   and takes business documents; allow about two weeks.
2. In MSG91, add the sender ID, map the DLT entity ID and create a template for
   each approved one, with `##VAR1##` and `##VAR2##` in place of `{#var#}`.
3. Set `MSG91_AUTH_KEY` and the four template IDs, then check with
   `cargo run --bin send_test_sms -- 9876543210`, which sends a real, billed SMS
   using the driver template.
4. Restart the API.

| Variable holding the ID | DLT template wording | `VAR1`, `VAR2` |
| --- | --- | --- |
| `MSG91_TEMPLATE_DISPATCH_CREATED_CUSTOMER` | `Hi {#var#}, your order (ref {#var#}) has been dispatched and is on its way. - BRAND` | customer name, order ref |
| `MSG91_TEMPLATE_DISPATCH_CREATED_DRIVER` | `New trip assigned: dispatch {#var#} to {#var#}. - BRAND` | order ref, customer name |
| `MSG91_TEMPLATE_DISPATCH_DELIVERED` | `Hi {#var#}, your order (ref {#var#}) has been delivered. Thank you! - BRAND` | customer name, order ref |
| `MSG91_TEMPLATE_DISPATCH_RUNNING_LATE` | `Hi {#var#}, your order (ref {#var#}) is running behind its expected delivery time. We're sorry for the delay. - BRAND` | customer name, order ref |

Replace `BRAND` with the registered business name. The text is duplicated in
`Notification::record_*`, so change both together; the `body` recorded there
leaves out the brand sign-off, which lives in the template.

MSG91's DLT rules shaped these: at most two variables, each value at most 40
characters (longer customer names are cut), the brand in every template, and a
variable can't be the last word. That's why the running-late SMS leaves out the
hours the email includes.

**`SENT` on an SMS means MSG91 queued it, not that the phone received it.** MSG91
checks some things after replying: tried on 2026-11-03, a made-up key got
`"type": "success"` on its first call and `Invalid authkey or Token` on the next,
even with the `realTimeResponse` option this code sends. So after any change to
the key or a template, confirm a test message actually arrives, and look at
MSG91's logs if customers report missing messages. Nothing here reads delivery
reports yet.

A message stays `QUEUED` until its template ID is set, so templates can go live
one at a time. Template text is Latin script for now: sending Hindi or Marathi
would need MSG91's `unicode` option and its own templates.

## Channel choice

- **Customer**: email if `Customer.email` is set, otherwise SMS to
  `Customer.phone`, otherwise `SKIPPED`.
- **Driver**: SMS to the driver's phone (drivers always have one), or
  `SKIPPED` if the vehicle has no active assigned driver.

## Customer contact details

`Customer` gained optional `phone` and `email`, set on
`POST /api/orgs/{id}/customers` (alongside name / address / coordinates) or
cleared/updated with `Customer::set_contact`. A blank string stores as `NULL`.
Fresh databases get the columns in `CREATE TABLE`; a long-lived local one is
patched by `ensure_contact_columns` (probe `information_schema`, `ALTER TABLE
ADD COLUMN`).

## Routes

| Method & path | |
| --- | --- |
| `GET /api/dispatches/{id}/notifications` | Notifications for one dispatch, oldest first (owned dispatch) |
| `GET /api/orgs/{id}/notifications` | The org's 100 most recent notifications, newest first |

Both are reads — any authenticated member of the org can see them.

## Frontend

- The **Customers** create form gained optional **Phone** and **Email** fields.
- The **Dispatches** page gained a **Notifications** column: a 🔔 toggle per
  row that expands a panel listing each recorded notification
  (status · recipient kind · channel → recipient · message). It refetches on
  open, so a delivered notification shows up after the status change.

## Tests

- Rust model (`notification/tests.rs`): created records customer + driver and
  prefers email; SMS fallback then `SKIPPED` with no contact; delivered
  notifies only the customer; `list_by_org` is scoped and newest-first;
  cascade delete with the org; `deliver_queued_best_effort` leaves `QUEUED`
  rows `QUEUED` without provider credentials and never touches a `SKIPPED`
  row; created/delivered fall back to the exact fixed template text without
  `ANTHROPIC_API_KEY`. Plus `Customer::set_contact` normalisation.
- Rust delivery (`notification/delivery.rs`): `deliver` returns
  `NotConfigured` for SMS/email without credentials (including an MSG91 key
  with no ID for that template); MSG91 gets the right template, number and
  variables against a fake local server, treats `"type": "error"` on HTTP 200
  as a failure, and never calls out for a junk number; phone normalization
  covers the stored formats; SMTP authenticates and sends a full message against
  a fake local server, rejects a malformed address or a line break in one, and
  reports an unreachable server as a provider error. MSG91, Resend and Gmail
  themselves are never called, matching this codebase's convention of never
  hitting a live third-party API in tests (see `ai/status.rs`'s equivalent note
  about the Anthropic call).
- Rust AI copy (`ai/notification_copy.rs`): each prompt
  builders includes the customer name, order reference and situation; each
  `generate_*` function errors with the missing-API-key message when
  `ANTHROPIC_API_KEY` isn't set — the only path tested, same convention as
  `notification/delivery.rs` above.
- Rust routes (`routes.rs`): creating a dispatch records two notifications
  (customer `SKIPPED`, driver `QUEUED` SMS); delivering records a
  `DISPATCH_DELIVERED` for the customer; the org feed is org-scoped (`403`
  otherwise); `POST /customers` stores contact details.
- Frontend unit: notifications api client; the Customers form passes contact
  details; the Dispatches page loads and shows a dispatch's notifications.
- Playwright (`notifications.spec.ts`): a customer created with an email gets
  it captured, a dispatch records notifications visible on the Dispatches
  page, and the org feed carries them. Full-flow demo has a "the customer and
  driver were notified" step; `npm run test:e2e:demo:notifications` is the
  standalone headed walkthrough.
